# 요청 시나리오 검증

작성일: 2026-09-10 · Evidence Remediation 19 · 로컬 실험 기능

후속 관찰: 같은 날 대화 안내를 받은 자가 보고 입력 7건을 확인했다.
[파일럿 결과](reports/2026-09-10_request_scenarios/participant_pilot.md)는 초기 자동 QA와 구분해 보존한다.

## 결론

[사용자 확정 요청 계약](structured_request_contracts.md)의 동작을 반복 검사하고,
구조화 입력의 어려움을 기록할 수 있는 검증 화면을 추가했다.

현재 자동 검사 결과는 **예상 동작 14개, 알려진 한계 1개, 회귀 실패 0개, 검사 오류 0개**다.
이는 모델 정확도나 안전성 100%를 의미하지 않는다. 모델 호출은 0회이며, 실행 대상은
준비된 합성 제안과 로컬 모의 핸들러다. 사람이 잘못 확정한 값은 여전히 탐지하지 못한다.

공식 상태는 `BLOCKED`, critical failure **110**, 실제 런타임 결과 **384**,
출력 검토 **0/30**, `not_production_ready`로 유지된다.

## 사용 순서

화면: [요청 시나리오 검증](http://localhost:3000/structured-requests/validation).
기존 `Request Contracts` 화면의 `시나리오 검증` 링크로도 진입한다.

### 자동 검사

1. `자동 검사` 탭에서 `15개 자동 검사`를 실행한다.
2. 예상 동작, 알려진 한계, 회귀 실패, 검사 오류를 각각 확인한다.
3. 판정 필터와 상세 보기로 원래 요청, 합성 제안, 예상/관측 HTTP, 차단 사유와 핸들러 호출을 비교한다.
4. 다운로드 아이콘으로 전체 JSON을 받는다. 이전 실행은 `최근 실행`에서 선택한다.

여기서 HTTP는 내부 서비스의 정상 응답 또는 `HTTPException` 상태를 관측한 값이다.
15개 각각에 대해 네트워크 HTTP 요청을 보내는 E2E 검사는 아니다. 네트워크/API 연결은
별도 smoke 검사로 확인했다. 실행 근거에는 팩 버전·해시와 관련 구현 파일 8개의 SHA-256이 담긴다.

### 입력 검증

1. `입력 검증` 탭에서 시나리오와 기록 출처를 선택한다. 기본 출처는 `자동 QA`다.
   실제 참여자가 직접 시도할 때만 `자가 보고 참여`를 선택한다.
2. `입력 검증 시작` 후 원래 요청을 읽는다. 값이 명확하면 `값 확정`을 선택하고 query와
   우선순위 값 또는 생략을 입력한다. 모순된 지시라면 `추가 확인 필요`를 선택한다.
3. `입력 저장` 후 저장된 JSON을 확인한다. 값 지정에는 자동 기본값이 없다.
4. 확인 체크박스를 선택한 뒤 `결과 제출`을 누른다. 수정하면 확인이 해제되며 재저장이 필요하다.
5. 제출 후 기준 입력과의 일치 여부, 불일치 항목, 경과 시간, 수정 저장 횟수를 확인한다.
   제출 기록은 최근 목록에서 다시 열거나 JSON으로 내보낼 수 있다.

이 화면은 **별도의 구조화 입력 연습**이다. 실제 요청 계약 화면에서 모델 생성과 실행까지
수행하는 전체 사용성 실험은 아니다. 제출이 티켓 생성이나 공식 검토 승인을 일으키지 않는다.
제출된 기록은 API에서 수정할 수 없으며, 다시 시도하려면 새 기록을 시작한다.

### 문자 차이 확인

제출 후 `query`가 불일치하면 결과 아래에 `query 문자 차이`가 표시된다.
`기준 query`와 `제출한 query`를 비교하고, 입력에 추가되거나 기준에서 빠진 문자를 강조한다.
공백은 `[SP]`, 탭은 `[TAB]`, 줄바꿈은 `[LF]`, 캐리지 리턴은 `[CR]`,
줄바꿈 없는 공백은 `[NBSP]`로 표시한다. 다른 비가시 문자는 `[U+200B]`처럼 코드로 표시한다.
문자 위에 포인터를 두면 해당 문자열의 1부터 시작하는 위치와 유니코드 코드 포인트를 확인할 수 있다.

예를 들어 SRC-03 파일럿의 `정기  점검 알림`은 기준보다 공백이 하나 많아,
제출값의 4번째 `[SP]`가 추가 문자로 강조된다. 기준은 8 코드 포인트/공백 2개,
제출값은 9 코드 포인트/공백 3개다. 글자 치환은 누락과 추가로 표시될 수 있다.

이 표시는 저장된 원문을 읽어 보여주는 기능이다. 자동 공백 정리, 유니코드 정규화,
입력 수정이나 재채점을 하지 않는다. 제출 전에는 나타나지 않으며, 우선순위만 불일치하는
기록에도 나타나지 않는다. [구현과 검증 기록](reports/2026-09-10_request_scenarios/query-diff/verification.md).

## 지표 해석

| 항목 | 실제 의미 | 의미하지 않는 것 |
| --- | --- | --- |
| 경과 시간 | 서버 시작 시각부터 최초 제출까지의 벽시계 시간 | 순수 작업 시간, 생산성 향상 |
| 수정 저장 횟수 | 첫 저장 이후 값이 달라진 저장 횟수 | 키 입력, 클릭, 저장하지 않은 수정 횟수 |
| 기준 일치 | 로컬 작성자가 정한 decision/query/priority와 정확히 일치 | 독립 전문가 검토, 일반적인 의미 이해 능력 |
| 자동 QA | 자동화 검사로 신고한 출처 | 참여자 사용성 결과 |
| 자가 보고 참여 | 참여자가 직접 수행했다고 신고한 출처 | 신원·실제 사람 참여에 대한 증명 |

새로고침과 다른 작업으로 기다린 시간도 경과 시간에 포함된다. 같은 값을 다시 저장하면
버전과 수정 횟수를 늘리지 않는다. 최초 저장은 수정 0회다. 제출 재요청은 기존 결과를 반환하며
시간이나 수정 횟수를 다시 계산하지 않는다.

초기 자동 QA 시점에 생성한 입력 기록 4개는 모두 `automated_qa`다.
이후 자가 보고 제출 7건은 위 파일럿 문서에 별도로 기록했다. `participant_self_report`를 선택하더라도
`human_review_verified: false`, `gate_evidence: false`는 변하지 않는다.

## 처리 구조

```text
버전 고정 시나리오 팩
  |-- 자동 검사 -> 일회용 SQLite -> 실제 요청 계약 서비스 -> 모의 실행/차단 관측
  |                                                        |
  |                                   별도 PostgreSQL 실행 보고서 + JSON 다운로드
  |
  +-- 입력 과제 -> 출처 고정 + 과제 스냅샷 -> 입력 저장(revision/hash)
                                            -> 별도 확인/제출
                                            -> 기준 비교 + 시간/수정 횟수
                                            -> 별도 입력 기록 + JSON 다운로드

공식 benchmark / Gate / human review 데이터: 위 두 경로에서 갱신하지 않음
```

자동 검사는 실제 저장·확정·검사·실행 서비스를 호출하지만 DB는 일회용 SQLite로 한정한다.
만료 시간 조작도 그 fixture DB 내부에서만 수행한다. 운영 API에는 만료 우회 입력을 추가하지 않았다.
시나리오별 예외는 `error`로 기록하고 나머지 검사를 계속하며, 반복 조회 영수증을 실행 횟수에
중복 합산하지 않는다. PostgreSQL에는 최종 보고서만 별도 테이블에 저장한다.

입력 기록은 서버 인증 미들웨어에서 얻은 소유자로 제한한다. 저장·제출 시 행 잠금과
optimistic version을 사용한다. 제출은 현재 revision과 SHA-256, 명시적 확인을 요구하고,
해시는 기록 ID·버전·출처·소유자·과제·입력을 결합한다. 출처는 시작 시 정하며 수정 API에 없다.
이는 API 수준의 무결성 경계이며 DB 관리자에 대한 변조 방지나 사람의 실제 확인을 증명하지 않는다.

Alembic `202609100001`은 이전 `202609090001` 뒤에
`request_scenario_runs`, `request_study_attempts` 두 테이블만 추가한다.

registry helper 내부에서 Tool 모듈을 지연 import하도록 좁게 수정했다.
고정된 과거 추론/진단 소스와 공식 증거 파일은 변경하지 않았다.

## API 계약

기준 경로: `/api/v1/request-scenarios`. 쓰기는 `x-model-atlas-lab-action: 1`을 요구한다.
기존 역할 검사, Origin 검사와 브라우저 세션 CSRF를 재사용한다.

| 메서드 / 경로 | 동작 |
| --- | --- |
| `GET /catalog` | 현재 팩과 입력 과제 목록, 제출 전 기준 입력 제외 |
| `GET /runs` | 소유자별 실행 보고서 목록 |
| `POST /runs` | 15개 동기 검사 후 보고서 저장, 201 |
| `GET /studies` | 소유자별 입력 기록 목록 |
| `POST /studies` | scenario_id와 source로 새 기록 시작, 201 |
| `GET /studies/{id}` | 저장된 입력 기록 조회 |
| `PUT /studies/{id}` | expected_revision과 answer로 저장 |
| `POST /studies/{id}/submit` | expected_revision/expected_hash/acknowledged로 제출 |

목록 기본 한도는 20개, 최대 50개다. 현재 UI는 최근 20개를 표시하며 전체 페이지 순회는 없다.
과거 결과는 저장 당시 팩과 입력을 보존하며 현재 팩으로 자동 재평가하지 않는다.

## 제한과 다음 단계

- 작은 로컬 작성 팩이며 query가 반복된다. 독립 검토된 holdout이나 다양한 실제 업무 표본이 아니다.
- 입력 API는 제출 전 정답을 제외하지만 자동 검사 보고서의 fixture에는 기준 입력이 포함된다.
  따라서 눈가림 실험이 아니며 사전 열람·반복 학습의 영향을 통제하지 않는다.
- 입력 연습의 편의성은 실제 요청 작성·확정·모델 생성·실행 전체 과정의 편의성과 다를 수 있다.
- 이번 격리 SQLite 검사는 PostgreSQL 동시성 증명이 아니다. 기존 단계의 동시 실행 검증과
  별도로 해석한다. 최신 구현의 실제 API 연결은 smoke 검사로 확인했다.
- 로컬 인증 비활성 상태의 `local-ui`는 공유·미검증 신원이다. 출처 선택은 사람 참여 인증이 아니다.
- 구조화 입력의 의미 오류, 외부 권한, 실제 티켓 생성의 멱등성 및 운영 보안은 해결하지 않았다.

다음은 실제 참여자의 입력 연습과 불편 사항을 자동 QA와 분리해 수집하는 것이다.
이후 새로운 문구·query를 가진 과제와 실제 계약 화면의 전체 작업 검증으로 넓힌다.
이 결과만으로 모델 후보 승격이나 공식 Gate 통과를 선언하지 않는다.
