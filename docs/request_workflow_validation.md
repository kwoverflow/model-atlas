# 실제 요청 흐름 검증 안내

작성일: 2026-09-10. Evidence Remediation 20.

## 이번 단계의 목적

입력 연습에서 한 단계 더 나아가, 실제 요청 계약 화면을 끝까지 사용할 수 있는지 관찰한다.
새로운 요청 10개를 `입력 → 저장 → 별도 확인 → 제안 비교 → 로컬 모의 실행 → 수행 종료`에 연결했다.
기존 SRC 입력 연습과 공식 모델 출력 검토는 별개의 작업이며 서로의 완료를 대체하지 않는다.

화면: [전체 흐름 검증](http://localhost:3000/structured-requests/workflow).
기존 시나리오 검증 화면의 `전체 흐름 검증` 링크에서도 접근할 수 있다.

이 팩은 이전 연습과 문구가 다른 **로컬 작성 개발·사용성 과제**다. 독립적으로 확보한 블라인드
평가 세트가 아니다. 자동 QA가 이미 실행한 과제이며, 제출 결과와 소스 코드에는 기준 답이 있다.
과제 번호별 정답을 이 사용 안내에 제시하지 않는다.

## 참여자가 하는 일

1. `기록 출처`가 `참여자 자가 보고`인지 확인하고 과제의 `시작`을 누른다.
2. 원래 요청을 읽고 query와 우선순위를 직접 결정한다. 실행 가능한 요청은 초안을 저장하고,
   저장된 값을 확인한 뒤 별도로 요청을 확정한다. 원래 요청은 이 화면에서 수정할 수 없다.
3. `로컬 모델 제안 생성`을 눌러 제안을 확인한다. 일치한 제안도 `모의 실행`을 직접 눌러야 실행된다.
   모델 제안이 틀렸다는 이유로 직접 고쳐서 모델의 성공으로 보고하지 않는다.
4. `수행 종료`에서 자신의 종료 결정, 도움 여부, 선택적인 난이도와 불편 사항을 기록한다.
   판단에 필요한 정보가 부족하면 `추가 확인 요청`, 중단했다면 `중도 중단`과 사유를 기록한다.
5. `종료 전 기록 확인`으로 저장 버전과 제안·실행 개수를 확인하고 체크박스 선택 후 제출한다.

한 번에 모두 할 필요는 없다. 목록의 수행 기록을 다시 열면 저장된 계약을 이어서 볼 수 있다.
과제를 새로 시작하면 기존 기록을 덮어쓰는 대신 별도의 시도가 생성된다.
종료 전 화면에서 `계속 수정`을 누르면 입력을 다시 수정할 수 있다.

`제안 JSON` 직접 입력은 수동 제안 검사 기능이다. 모델 생성과 별도 출처로 집계되며,
수동 제안으로 완료한 수행을 모델 정확도 검증으로 해석하지 않는다.

도움을 요청할 때 `도움 요청 기록`을 누를 수 있다. 대화에서 조작이나 과제 해석에 도움을 받았다면
종료 시 도움 여부와 내용을 사실대로 기록한다. 도움 없음도 자가 보고일 뿐 독립성 증명이 아니다.
자동 QA를 사람이 수행한 것처럼 출처를 바꿀 수 없다.

## 자동으로 보존되는 항목

| 항목 | 의미와 제한 |
| --- | --- |
| 과제 팩 버전·해시 | 시작 시 요청문과 기준 답을 스냅샷으로 보존한다. |
| 연결된 실제 계약 | 과제당 하나의 새 계약만 원자적으로 생성·연결한다. 기존 계약을 가져오지 않는다. |
| 재저장 횟수 | 첫 저장 이후 모든 초안 저장 횟수. 동일 값 재저장도 포함하며 키 입력 횟수가 아니다. |
| 경과 시간 | 서버 시작부터 종료까지의 시간. 대기·새로고침·서비스 복구 시간을 포함한다. |
| 제안 출처·차단·실행 | 저장된 모델 제안, 직접 입력 제안, 차단된 제안, 실행 기록을 따로 센다. |
| 도움 요청 | 사용자가 버튼으로 보고한 횟수. 실제 도움 제공 횟수나 인원 수가 아니다. |
| 종료 결정·피드백 | 완료·추가 확인 요청·중단, 도움 여부, 난이도, 자유 의견. |
| 제출 증거 | 모든 제안과 실행을 포함한 계약 스냅샷 및 SHA-256. |

모델 제안 개수는 HTTP 요청 수와 다르다. 기존 생성 어댑터는 제안 하나를 만들 때 여러 번
요청할 수 있다. 제안 레코드를 만들지 못한 생성 오류는 이 개수에 포함되지 않으므로,
오류 상황은 피드백·검증 보고서에 별도로 남겨야 한다. 현재 순수 작업 시간이나 오류 발생률은 측정하지 않는다.

## 결과 해석

- `과제 기준 일치`: 이 시도의 저장값·종료 결정·실행 기록이 로컬 과제 기준과 맞았다는 뜻이다.
  모델의 일반 정확도, 사용자 모집단의 성공률, 독립 검토 완료 또는 운영 승인을 의미하지 않는다.
- `과제 기준 불일치`: query·우선순위·종료 결정·실행 여부 등 구체적인 사유를 표시한다.
  query 차이가 있으면 제출 후 문자별 공백·추가·누락을 보여준다. 문자열을 정규화하거나 고치지 않는다.
- `중단`: 실패나 성공에 조용히 합산하지 않는다. 진행 중인 기록도 별도 집계한다.
- 과거 버전에서 잘못 실행한 뒤 값을 고쳐 다시 실행해도, 이전 실행 인자의 불일치는 남는다.

집계는 **시도 수**이며 사람 수가 아니다. 팩 해시·자동 QA/참여자 출처·도움 여부별로 분리한다.
현재 신원은 공유 `local-ui`일 수 있어 독립된 참여자 수나 실제 사람의 확인을 검증할 수 없다.

## 구조와 보존 범위

`request_workflow_catalog.py`는 과제 정의, `request_workflows.py` 서비스는 소유권과 과제 생명주기,
API 라우트는 인증 경계와 입출력 연결을 담당한다. 프런트엔드는 기존 `StructuredRequestLab`을
재사용한다. 모델 입력이나 인자 생성 로직에 과제 기준 답을 주입하지 않는다.

새 `request_workflow_attempts` 테이블 하나를 Alembic `202609100002`로 추가했다.
기존 47개 테이블의 메타데이터 해시와 앞선 실험 테이블은 그대로 보존한다.
계약 생성과 연결은 하나의 트랜잭션이다. 과제 수정은 버전으로, 종료는 버전과 전체 계약 상태
해시로 묶는다. 조회 이후 제안이나 실행이 추가되면 오래된 종료 요청을 409로 거절한다.

제출한 과제 결과는 API로 수정할 수 없고 동일 요청의 재전송은 기존 결과를 반환한다.
다만 연결된 일반 요청 계약 자체를 영구 봉인하는 기능은 아니다. 다른 요청 계약 화면/API에서
나중에 수정·실행하더라도 **이미 제출한 스냅샷은 바뀌지 않는다**. 제출 이후의 활동을 그 결과가
대표한다고 해석해서는 안 된다. 추가 확인 요청은 기록된 종료 결정이며 외부 사람에게 메시지를
전송하거나 실제 답변을 받았다는 뜻도 아니다.

## 다운로드 검증

`수행 기록 JSON`에는 표시용 결과와 `evidence.canonical_json` 문자열이 함께 들어 있다.
브라우저는 숫자 `0.0`을 `0`으로 바꿀 수 있으므로 표시용 객체를 임의로 다시 직렬화해 해시를
계산하지 않는다. 포함된 canonical JSON의 UTF-8 바이트가 `evidence.sha256`의 계산 대상이다.

프로젝트 루트에서 내려받은 파일을 검증한다.

```powershell
.venv/Scripts/python.exe tools/verify_request_workflow_export.py "C:/Users/rokn2/Downloads/request-workflow-<기록 ID>.json"
```

이 도구는 canonical 바이트의 해시뿐 아니라 표시 결과, 시도 ID, 출처가 일치하는지도 확인한다.
해시는 전자서명이나 본인 인증이 아니다. 양쪽 데이터와 해시를 함께 위조한 사람까지 검출하지 않는다.
초기 내보내기에는 canonical 문자열이 없었다. 해당 파일은 현재 화면에서 같은 기록을 다시
내려받으면 된다. 원래 DB 제출 내용이나 해시를 고쳐 쓰지 않았다.

## 실행과 다음 단계

Docker와 기존 모델이 준비된 환경에서는 다음 명령으로 필요한 서비스를 시작한다.

```powershell
docker compose --profile runtime up -d db backend frontend ollama
docker compose --profile runtime exec -T ollama ollama list
```

생성 기능은 기존 `qwen2.5:1.5b`를 사용한다. 모델이 없으면 별도 준비가 필요하며 과제 시작만으로
모델을 내려받지 않는다. 실제 외부 티켓 서비스에는 연결하지 않는다.

다음 단계는 사람이 새 과제를 직접 수행한 결과를 수집하고 확인 부담과 중단 이유를 분석하는 것이다.
그다음 기존 20개 실패 그룹의 원인별 개선과 실제 모델 출력 검토를 진행한다.
공식 상태는 여전히 `BLOCKED / 110 critical failures / 384 runtime results / output review 0/30 /
not_production_ready`다. 이번 UI·자동 QA 완료가 공식 Gate 통과를 대신하지 않는다.
