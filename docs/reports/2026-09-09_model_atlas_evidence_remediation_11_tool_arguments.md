# Model Atlas Tool 인자 검증 리뷰

작성일: 2026년 9월 9일. 범위: Evidence Remediation 11.

## 결론

이번 단계는 모델 성능 향상이 아니라 **인자 보정에 의존한 성공과 실제 모델 출력을 구분하는 개선**입니다.
모델이 생성한 인자를 그대로 검증하고, 검증에서 막힌 호출은 도구 실행도 건너뛰도록 변경했습니다.

기존 원본 출력 72건을 감사한 결과, 과거 성공 56건 중 46건이 새 기준에서는 차단됐습니다.
다만 장애 주입 허용 정책과 문서 ID 확인 기준도 강화했으므로, 46건 모두를 과거 채점 오류로 단정하지 않습니다.
새로운 실제 실행에서는 도구 선택 44/48건, 실행 성공 5/48건이었습니다. **출시 승격 근거로 사용할 수 없습니다.**

## 지표와 실험 범위

| 구분 | 관측 단위와 표본 | 실제 수행 내용 |
| --- | --- | --- |
| 오프라인 감사 | 추가 요청 24개 x 구성 3개 x 시행 1회 = 72건 | v20 저장 원본에 v2 검증 적용. 추론과 도구 재실행 없음 |
| 실제 실행 | finalized 1.0.4의 일반 Tool 10개 + 복구 6개, 구성 3개 = 48건 | Docker/Ollama에서 새 추론 및 로컬 fixture 실행 |
| 공식 Gate | 기존 canonical 증거 384건 | 읽기 전용 상태 확인. 이번 진단으로 승격하거나 덮어쓰지 않음 |

- 선택 정답: 모델이 요청에 맞는 도구를 골랐는지 확인한 값입니다.
- 스키마 유효: 공개 Tool 스키마의 타입, 필수 필드 등의 조건을 만족한 값입니다.
- 실행 허용: 스키마와 문서 ID 목록, 장애 주입 정책까지 만족한 값입니다. 실행 성공을 뜻하지 않습니다.
- 실행 인자 유효: 실행 시 공개 스키마, 기존 평가 스키마, guard 조건을 모두 반영한 값입니다.
- 실행 성공: 기존 평가와 결정론적 로컬 fixture가 성공한 값입니다. 실제 외부 업무 성공이나 질의의 의미적 정확성이 아닙니다.

두 실험은 사례, 입력, 프롬프트 경로가 다릅니다. 오프라인 감사의 과거 입력에는 새 문서 목록이 없었습니다.
서로 다른 두 실험을 하나의 모델 성능 전후 비교로 합치지 않습니다.

## 기존 출력에서 확인한 문제

| 구성 | 관측 수 | v1 성공 | v2 스키마 유효 | v2 실행 허용 | 선택 정답 + v2 허용 | 이전 성공 중 새 차단 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.5B 기본 | 24 | 12 | 17 | 11 | 6 | 6 |
| 1.5B 후보 | 24 | 22 | 15 | 2 | 2 | 20 |
| 1.5B 프롬프트 변형 | 24 | 22 | 18 | 2 | 2 | 20 |
| 합계 | 72 | 56 | 50 | 15 | 10 | 46 |

v1은 53건의 인자를 바꿨습니다. 원본의 인자 유효 50/72건이 보정 후에는 72/72건이 됐습니다.
이는 원본 모델 출력이 100% 정확했다는 뜻이 아닙니다. 새 정책에서 허가되지 않은 장애 주입은 49건,
문서 목록에 없는 ID는 9건, query 누락은 2건이었습니다. 사유가 중복되므로 합산하면 안 됩니다.

코드상으로는 요청 문장을 문서 ID로 채우거나, 문자열을 잘라 의미를 바꾸거나, 자연어 부정문을 장애 주입으로
잘못 해석할 수 있는 경로도 확인했습니다. 그러나 이 72건에서는 document_id 자동 채움이 관측되지 않았습니다.
코드상 가능한 위험과 실제 관측된 사례를 구분했습니다.

근거: `artifacts/reference-workload/tool-argument-contract-audit-v21.json`.

## 새 실제 실행 결과

| 구성 | 실행 수 | 선택 정답 | 실행 인자 유효 | 실행 성공 |
| --- | ---: | ---: | ---: | ---: |
| 0.5B 기본 | 16 | 12 | 5 | 4 |
| 1.5B 후보 | 16 | 16 | 1 | 1 |
| 1.5B 프롬프트 변형 | 16 | 16 | 0 | 0 |
| 합계 | 48 | 44 | 6 | 5 |

일반 Tool은 5/30건 성공, 복구 사례는 0/18건 성공했습니다. 이번 기본 구성은 장애 주입을 허용하지 않지만
기존 복구 평가는 simulate_failure를 요구합니다. 인자를 자동 삽입하지 않기 때문에 이 조건의 충돌이 실패에
포함됩니다. 이를 복구 능력의 공정한 전후 비교나 모델 자체의 성능 저하로 해석하면 안 됩니다.

48건 모두 추론 결과를 저장했으며, 타임아웃과 OOM은 0건입니다. 실행 환경은 Ollama 0.31.1,
qwen2.5:0.5b / qwen2.5:1.5b Q4_K_M, seed 42, temperature 0, max_tokens 384,
구성별 1회 시행·동시성 1입니다. Tool 선택은 기존 legacy 프롬프트 경로이며, 공개 문서 목록을 새로 제공합니다.

새 guard가 차단한 36건은 모두 handler 실행 시도 0회였습니다. 기존 평가 조건과 선택 실패까지 포함하면
총 43건이 실행을 건너뛰었습니다. 48건의 원본·정규화 인자 해시 불일치는 0건입니다.
문서 ID 4건은 corpus에 존재했고, 5건은 목록에 없었습니다. 존재 확인은 요청에 맞는 문서라는 판정이 아닙니다.

근거: `runtime-matrix-diagnostic-tool-argument-v21.json`과 `tool-argument-runtime-audit-v21.json`.

## 구현 구조

1. `benchmark_execution.py`: 설정된 corpus를 해시·버전과 대조하고 실제 chunk에서 문서 ID 목록을 만듭니다.
   다른 corpus를 합치지 않으며, 외부에서 넘긴 내부 context는 서버에서 준비한 값으로 교체합니다.
2. `tool_call_contract.py`: 단일 호출의 형식과 인자를 검증합니다. 누락 값 채움, 필드 삭제, 타입 변환,
   공백 제거, 문자열 자르기를 하지 않습니다. 문서 목록과 명시적인 장애 주입 설정을 별도로 검사합니다.
3. `openai_compatible.py`: adapter v21에서 검증기를 연결하고 원본 응답과 감사 메타데이터를 보존합니다.
4. `tool_execution.py`: 거절된 호출은 handler 실행 전에 중단하고 선택 결과와 실행 실패를 별도 trace로 남깁니다.

중복 JSON 키, 비표준 숫자, 모호한 호출, 미등록 Tool, 지원하지 않는 스키마 제약은 거절합니다.
JSON Schema 전체 구현이 아니라 명시적으로 지원하는 제한된 부분집합이며, 알 수 없는 제약을 무시하지 않습니다.

장애 주입은 runtime_config_json.tool_failure_simulation 설정으로만 허용합니다.
transient_once 또는 permanent가 가능하며, 모델이 이미 생성한 일치하는 인자만 허용합니다.
자연어의 재시도 문구에서 값을 추론해 삽입하지 않습니다. 기존 설정과 잠긴 평가 사례는 자동 수정하지 않았습니다.

기술 설명과 재현 명령: `docs/tool_argument_validation.md`.

## 불확실성과 남은 범위

- locally authored 사례이며 독립 외부 시험셋이나 생산 트래픽이 아닙니다. 일반화 성능은 확인하지 않았습니다.
- 단일 시행이며 프롬프트 및 도구 목록 순서 민감도가 남아 있습니다. 새 문서 목록도 출력 변화에 영향을 줍니다.
- 질의 적합성은 not_verified입니다. 스키마가 맞는 query도 실제 의도와 다를 수 있습니다.
- 문서 ID 존재 여부는 내용, 사용자 접근 권한, 문서 선택 적합성까지 증명하지 않습니다.
- guard는 standalone Tool 경로에 한정됩니다. Agent·RAG·다단계 및 legacy 직접 실행 경로 전체에 적용한 것은 아닙니다.
- fixture 성공을 실제 문서 조회나 외부 업무 성공으로 해석하면 안 됩니다.
- 공식 Gate는 BLOCKED, critical 실패 110건, 증거 384건, 모델 출력 사람 검토 0/30건,
  production 준비 상태 not_production_ready를 유지합니다. 소스 사례 승인과 모델 출력 승인은 별개입니다.

## 권장 다음 단계

1. 장애 주입을 모델 인자에서 시험 환경으로 분리합니다. 정상 실행과 복구 실행의 계약·버전·결과를 구분합니다.
2. 선택된 Tool 스키마와 실제 문서 목록으로 인자를 생성하는 별도 후보 경로를 시험합니다. 자동 보정은 복구하지 않습니다.
3. 실제 문서 조회와 접근 권한을 연결하고, 질의와 문서의 적합성을 검증할 독립 사례를 추가합니다.
4. 반복 시행, 전체 workload 회귀, 실제 출력 검토를 마친 뒤에만 증거 승격과 Gate 재평가를 진행합니다.

남은 질문은 인자 생성 분리가 늘리는 토큰·지연 대비 정확도 효과, 기존 복구 계약의 마이그레이션 범위,
Agent·RAG·다단계 경로에 동일 원칙을 적용할 때의 호환성입니다.
