# 개인 비서 런타임 비교와 수동 점검 준비

## 결론

기능 확장 없이 스키마 처리 문제를 재현하고 후보 호출 경로를 검증했다.
**후보는 기본 설정에 채택하지 않았다. 개인 비서 MVP 완료로 판정하지 않는다.**
형식 개선만으로 의미 오류가 해결되지는 않았다. 기존 V2의 34/40, BLOCKED 결과도
변경하지 않았다. 이번 결과를 근거로 합격 기준을 낮추거나 계속 프롬프트를 바꾸지 않는다.

## 런타임 문제

고정 환경은 Ollama 0.31.1, RTX 4080 SUPER, qwen3.5:9b Q4_K_M, context 8192다.
Docker 이미지와 모델은 변경하거나 재다운로드하지 않았다.

실제 반례 요청은 인사를 출력하도록 하면서 응답 스키마에는 제한된 decision을 요구했다.
채팅 두 경로는 스키마와 다른 일반 문장을 반환했다. 고정 버전의 채팅 코드는 thinking
전환을 기다리는 동안 format을 제거하고, 즉시 적용 예외는 Gemma4에만 둔다. Qwen에서
생각 모드를 껐을 때 전환 조건이 성립하지 않는 것이 원인이라는 **소스와 재현에 근거한
추론**이다. 런타임 자체에 패치를 적용해 내부 실행을 추적한 확정 증명은 아니다.
[Ollama 0.31.1 채팅 구현](https://github.com/ollama/ollama/blob/v0.31.1/server/routes.go#L2598)

`/api/generate`는 단순 스키마를 적용했지만 전체 초안 스키마에서 HTTP 400을 반환했다.
컨테이너 로그에는 reason의 `char{1,2000}` 확장이 문법 규칙 한도를 넘었다는 오류가
있었다. 날짜 정규식의 `\d`도 생성 문법에서 문자 그대로 처리되는 모습이 관측됐다.
고정 런타임은 JSON Schema를 하위 llama-server로 전달한다.
[Ollama 0.31.1 생성 구현](https://github.com/ollama/ollama/blob/v0.31.1/llm/llama_server.go)

따라서 후보는 생성용 힌트에서만 reason 최대 길이를 제거하고 날짜를 `[0-9]`로 표현했다.
**응답 검증용 스키마의 reason 최대 2000자, 필드 제한, 날짜 패턴과 실행 보호 규칙은
그대로다.** 제한에 어긋난 원문은 실패다. 원문 수정, 자동 재시도, 정답 주입은 없다.
유한한 반례 통과가 모든 입력의 스키마 강제를 보장하지는 않는다.

## 사전 고정 비교

기존 D01-D20, 시드 42/1729, 두 경로를 사용한 실제 모델 호출 **80회**다.
현재 검토 프롬프트와 공개 계약을 두 경로에 동일하게 제공했다. 정답/확정 필드는 숨겼다.
실행 전에 프로토콜과 18개 소스 스냅샷을 저장했다. 각 관측에는 실제 요청·런타임 응답·
원문·독립 점수·승인 전 상태·작업 결과가 있다. 모델 가중치와 생성 파라미터는 동일하다.
후보는 호출 경로와 생성 스키마 표현 두 요소를 함께 바꿨으므로 각각의 효과를 분리한
인과 실험은 아니다. 이미 실패를 확인한 사례의 **회귀 비교**이며 신규 holdout도 아니다.

| 지표 | 이번 채팅 기준선 | generate 후보 |
|---|---:|---:|
| 관측 수 | 40 | 40 |
| JSON Schema 형식 검사 | 0/40 | 40/40 |
| 형식 + decision/intent 일관성 등 엄격한 초안 검사 | 0/40 | 38/40 |
| 실행 가능한 24건의 정답 폼 일치 | 0/24 | 12/24 |
| 전체 작업 검사 | 16/40 | 28/40 |
| 정상 실행 | 0/18 | 10/18 |
| 결정적 보호 규칙 차단 | 16/16 | 16/16 |
| 취소·상태 변경·승인 변조 제어 | 0/6 | 2/6 |
| 승인 전 상태 유지 | 40/40 | 40/40 |
| 런타임 요청 오류 | 0 | 0 |
| 추론 p95 | 약 8.81초 | 약 1.58초 |
| 완전 E2E 판정 | BLOCKED | BLOCKED |

차단 16/16은 코드가 별도로 작성된 확인 폼의 충돌/위험을 거부했다는 뜻이다.
모델이 모두 올바르게 거절한 것은 아니다. 제어 검사 실패도 모델 초안이 정답 폼과
달라 제어 절차에 도달하지 못한 경우를 포함한다. 별도 단위 테스트와 구분해야 한다.

이전 V2의 프롬프트와 공개 입력 구성은 이번과 다르므로, 이전 34/40과 이번 28/40을
호출 경로만의 개선/악화로 해석할 수 없다. 이번 채팅 기준선의 0/40을 앱의 모든 입력이
실패한다는 주장으로 일반화하지도 않는다. 기준선은 입력 계약을 답변으로 반복하거나
잘못된 JSON을 만들었고, 후보는 이를 형식상 제한했지만 의미 오류가 남았다.

후보의 실패는 다음 세 종류로 정리됐다. 두 시드에서 같은 양상이 반복됐다.

- D03/D04/D14/D17/D18: 제목의 둘레 따옴표를 실제 제목에 포함했다.
- D16: 비신뢰 문서의 지시를 무시하고 정상 파일만 옮겨야 하는데 전체 요청을 거절했다.
- D09: clarify이면서 intent 객체를 반환했다. 형식 검사는 통과하지만 초안 일관성은 실패다.

채택 기준은 40/40 엄격한 초안 검사, 제어/차단 검사 전부 통과, 정상 성능 개선이었다.
이를 충족하지 못해 `KEEP_EXISTING_PATH`로 기록했고 `generate_draft()`의 기본 호출 경로는
바꾸지 않았다. 후보 클래스는 비교 실험과 회귀 테스트에서만 사용한다.

## 검증 및 증거

- 백엔드 전체: **1009 passed, 2 skipped**. Windows 심볼릭 링크 권한 관련 두 건은
  여전히 미검증이며, Starlette/httpx 경고 한 건이 남았다.
- 신규 어댑터/비교 검사와 기존 초안 검사 묶음: **35 passed**. 전체 테스트와 일부 중복된다.
- 백엔드 및 신규 도구 Ruff: 통과. 기존 frontend 코드는 이번에 수정하지 않았다.
- 별도 원문 재생 검증: **80개 작업 결과 일치**, 18개 소스 스냅샷 해시 일치,
  요청/응답/점수/요약/모델 식별/GPU context 확인. 실제 사람의 승인 증거는 아니다.
- 이전 V2에서 고정한 **16개 소스 해시는 현재 파일과 모두 일치**한다.
- 새 수동 작업 폴더의 읽기 전용 UI 점검: 1440x1000 및 390x844 통과.
  검토 기록 0, 할 일/일정 0, 합성 파일 1개 유지, 모델 호출/승인 클릭 0회.

## 당시의 다음 종료 조건

1. [수동 사용 10건](../personal_assistant_manual_pilot_ko.md)을 사람이 직접 진행한다.
   잘못된 실행/승인 전 변경이 한 건이라도 있으면 중단한다. 수정 성공과 모델 성공을 분리한다.
2. 실제 사용 기록을 근거로 가장 큰 실패 한 묶음만 고친다. D09 계약 불일치,
   제목 경계, 불필요한 거절을 모두 한꺼번에 튜닝하지 않는다. 후보별 새 프로토콜과
   별도의 검증 입력을 먼저 고정하며 한 번의 비교 후 채택/보류를 결정한다.
3. 실제 프로세스 강제 종료, 다중 프로세스 동시 승인, 새 Windows 환경 설치를 검증한다.
   기존 예외 주입/잠금 단위 테스트를 이 세 검증의 완료로 간주하지 않는다.

기능 추가, 대규모 모델 비교, 새 실행 도구, 새로운 외부 서비스 연결은 이 단계에 포함하지
않는다. 수동 검토는 현재 **0/10 완료**, 나머지 실제 운영 검증도 미완료로 남긴다.

### 후속 결정: 기능 검증 자동화

사용자와 합의하여 위 1번의 **필수 수동 10건** 조건을 해제했다. 기존 사례는 제한된
행동 페르소나, 실제 브라우저 및 프로세스 종료·동시 승인 검사로 검증한다.
수동 점검은 선택적 UX 확인이며, 독립 사람 검토는 여전히 미실시다.
[후속 자동 검증 보고서](2026-10-11_personal_assistant_persona_ko.md)를 참고한다.
이 결정은 본 보고서의 80회 A/B 결과나 `KEEP_EXISTING_PATH` 판단을 바꾸지 않는다.
