# 개인 비서 검토 흐름 고도화 결과

## 결론

기능 확장을 멈추고 기존 작업의 초안 수정·확정·승인·복구를 구현했다.
현재 단계는 **사용자 검토형 로컬 샌드박스 데모**다. 개인 비서 MVP 완료 또는 모델 추천 승인으로
표현하지 않는다. 기존 EvalOps MVP와 개인 비서 실험의 완료 범위는 서로 다르다.

## 개선한 문제

이전 V2 흐름은 모델 초안과 확인 값이 정확히 같아야 했다. 사용자가 따옴표가 들어간 제목이나
잘못된 날짜를 고쳐도 거절됐다. 새 흐름은 원문과 사용자 수정본을 별도로 저장하고, 명시적으로
확정한 수정본에서 코드가 실행 계획을 만든다. 사용자 수정 후 성공한 결과는 모델 정답이 아니다.

- 실제 편집 폼, 수정 저장·취소, 확인 체크박스, 변환된 실행 미리보기, 별도 승인·취소를 연결했다.
- 확정·수정마다 버전을 갱신해 오래된 창이나 이전 승인의 실행을 차단한다.
- 중복 실행 요청은 기존 결과를 반환하며, 실행과 결과 재확인을 처리 기록에서 구분한다.
- 파일 이동·보관의 복구는 원래 실행과 별도 기록 및 새 승인을 사용한다.
- 파일 작업 중단 시 원본·대상 경로, 내용 해시, 동일 파일 여부와 링크 수를 대조한다.
  부작용 없음, 부분 링크의 원복, 이미 완료된 효과의 기록만 처리하고 모호한 변경은 차단한다.
- OS 잠금으로 진행 중인 실행과 복구가 겹치지 않게 했다. 프로세스 종료 시 잠금이 해제된다.
- 사용자별 작업공간과 기존 역할·Origin·작업 헤더 검사를 적용하고 원문 승인 토큰은 API에서 숨긴다.
- 입력 폼과 작업공간 표시를 분리하고, 버튼 대비·모바일 배치·미저장 수정 보호를 개선했다.
- 초기 화면의 비동기 로딩을 정리하고 승인 대기 상태에만 만료 타이머를 동작시킨다.
  상태 조회가 실패하면 이전 값을 현재 상태처럼 표시하지 않는다.

사용 절차와 코드 책임은 [사용 및 유지보수 안내](../personal_assistant_review_ko.md)에 정리했다.

## 실제 검증

환경은 기존 RTX 4080 SUPER 16GB, Qwen3.5 9B Q4_K_M, Ollama 0.31.1, 8K 문맥이다.
개인 파일이나 외부 캘린더 대신 새 작업공간과 합성 파일을 사용했다.

| 검증 | 결과 |
| --- | --- |
| 백엔드 전체 회귀 | 1,001 통과, 2 건너뜀 |
| 새 검토 흐름 테스트 | 29 통과 |
| 기존 프런트엔드 단위 테스트 | 29 통과 |
| Ruff, TypeScript, 프로덕션 빌드 | 통과 |
| ESLint | 오류 0, 기존 내비게이션 경고 4 |
| 실제 모델 연결 브라우저 E2E | 수정·확정·승인, 지속성, 취소, 오래된 승인 차단, 시각 변환, 파일 복구 검증 통과 |
| 화면 검사 | 1440×1000 및 390×844, 가로 넘침·실행 버튼 색상·페이지 오류 검사 통과 |

건너뛴 2개 테스트는 Windows 심볼릭 링크 생성 권한 문제다. Starlette TestClient의 기존
httpx 사용 폐기 경고도 남아 있다. 이 두 영역의 검증 완료를 주장하지 않는다.

최종 전체 브라우저 검증 `browser-v4`는 실제 모델 요청 8건을 포함한다.
원본 응답의 JSON Schema 검증은 6/8이며 2건은 원본 검증 실패로 기록됐다.
직접 폼 수정·저장한 경로는 5건이다. 형식 검증 성공도 의미 정확성을 보장하지 않는다.
파일 보관 요청을 이동으로 해석한 사례처럼 의미 오류도 남아 있다.
7개 흐름 검증 그룹이 통과한 것은 **자동화된 사용자 수정·승인 후의 흐름**을 검증한 결과다.
원본 초안의 정답률, 실제 사용자 생산성, 독립 인간 검토 통과율이 아니다.

## 런타임에서 발견한 한계

[Ollama 공식 문서](https://docs.ollama.com/capabilities/structured-outputs)는 JSON Schema를
`format` 또는 OpenAI 호환 `response_format`으로 전달하는 방법을 설명한다.
그러나 현재 고정 런타임에서 간단한 enum 계약과 전체 초안 계약을 각각 두 API로 요청한
4개 반례가 모두 계약을 위반했다. 스키마 요청을 했다는 이유만으로 강제 디코딩을 주장할 수 없다.

따라서 메타데이터를 `schema_requested`와 실제 후검증 결과인 `schema_valid`로 구분한다.
응답을 자동 복구하거나 성공으로 재표시하지 않는다. 스키마를 공개 입력에도 전달하지만,
그것이 강제 적용 보장이나 의미 정확성 개선 증거는 아니다.
기존 V2 평가의 34/40 흐름 통과 및 `BLOCKED` 결과는 변경하지 않았다.
V2 프로토콜에 기록된 16개 소스의 SHA-256도 현재 파일과 일치하는 것을 확인했다.

## 증거 위치

아래 자료는 로컬 `artifacts/personal-assistant-review/2026-10-11/`에 있으며 기본적으로 Git에서
제외된다. 원문 요청·SQLite·화면 캡처를 승인 없이 공개 저장소로 업로드하지 않는다.

- `browser-v4/browser-e2e.json`: 원문, 원본 필드, 수정본, 모델 메타데이터, 검증 결과와 최종 상태.
- `browser-v4/desktop-preview.png`, `desktop-executed.png`, `mobile-executed.png`, `mobile-files.png`.
- `schema-enforcement-probe.json`: 두 API의 실제 요청 및 응답, 스키마 반례 결과.
- `local-pilot-v4/`: 사용자별 SQLite, 합성 파일, 실행 로그. 파일 복구 후 초기 내용 해시가 유지됐다.

초기 실패 기록도 보존했다. 모델 원문의 오류를 숨기기 위해 성공 결과로 덮어쓰지 않는다.
모든 브라우저 승인은 테스트 자동화이며 `independent_human_attestation=false`다.

## 당시의 다음 개선 순서

1. **모델·런타임 신뢰성:** 기존 고정 평가 사례로 제한된 개선안을 재평가한다. 현재 런타임의
   스키마 적용 문제를 해결하거나 미지원 상태를 명시한다. 자동 초안 품질과 사용자 수정 후
   실행 품질을 분리하며 기존 수락 정책을 낮추지 않는다.
2. **실제 사용자 검토:** 이번 화면으로 기존 5개 작업 범위 안에서 10건의 수동 사용을 기록한다.
   요청 대비 수정 항목, 잘못된 실행, 취소·만료, 복구 결과를 확인한다. 잘못된 실행이 있으면
   보류하고 원인을 수정한다. 자동 클릭 기록을 인간 확인 증거로 사용하지 않는다.
3. **출시 전 안정화:** 실제 프로세스 종료·동시 접근, 링크 경계의 권한 있는 Windows 검증,
   새 환경 재설치와 시작·복구를 반복한다. 남은 경고와 운영 오류를 해결하고 체크리스트로 닫는다.

새 기능, 추가 모델 수, 외부 계정 연동으로 범위를 넓히지 않는다. 실제 연동, 광범위한 파일 탐색,
대규모 상태의 문맥·메모리 관리, 생산 환경 권한 및 독립 검토 증거는 아직 검증하지 않았다.

2026-10-11 후속 합의로 2번의 필수 수동 점검은 자동 기능 검증으로 대체했다.
선택적 사용자 UX 점검과 독립 검토 증거는 구분하여 미검증으로 남긴다.
[페르소나·브라우저·실제 프로세스 검증 결과](2026-10-11_personal_assistant_persona_ko.md)는
후속 증거이며 위 역사적 V2/V4 결과를 다시 채점하지 않는다.
