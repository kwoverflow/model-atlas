# 우선순위 의도 검증과 실행 차단 실험

검증일: 2026-09-09. Evidence Remediation 17.

## 판단

**별도 검증기는 기존 low 누락을 차단했지만, 기본 실행 경로에 적용할 수준은 아니다.**
같은 소형 모델로 의도를 재해석하면 생성 오류를 일부 잡을 수 있으나, 정상 호출을 막거나 상충 지시를 통과시키는 문제가 남는다.
따라서 이 후보는 진단용으로 보존한다. 모델 가중치, 기본 어댑터, API 등록, 공식 Gate를 변경하지 않는다.

이번 단계는 더 나은 인자를 생성하는 실험이 아니라 **이미 생성된 호출을 실행해도 되는지 확인하는 실험**이다.
차단을 성공적인 업무 완료로 세지 않으며, 모델이 잘못 생성한 값을 정답으로 고쳐 넣지 않는다.

## 측정 결과

### 개발 확인

호환성을 수정한 v1.1의 개발 관측 32건에서 잘못된 허용은 13건에서 3건으로 줄었다.
그러나 정상 제안 19건 중 8건을 차단하여 exact 완료도 19건에서 11건으로 감소했다.
기존 high 회귀는 4/4 그대로 허용했고, low 누락은 4/4 차단했다. low 인자를 복구하거나 업무를 완료한 것은 아니다.
상충 지시 요청의 네 번 반복 중 세 번은 여전히 통과했다.

### 새 요청의 안전성과 완료율

총 64건은 실행 가능한 요청 52건과 확인이 필요한 요청 12건이다. 16개 요청을 네 번씩 반복한 관측이며 독립 요청 64개가 아니다.

| --- | ---: | ---: |
| 실행 허용 | 64/64 | 32/64 |
| exact 업무 완료 | 40/52 | 28/52 |
| 기본값 동등 업무 완료 | 40/52 | 28/52 |

| 생성 또는 생성+검증 지연 중앙값 | 3.136초 | 4.173초 |

검증기가 잘못된 제안 20건을 차단한 대가로 정상 제안 12건도 차단했다. 정상 제안 차단율은 30%다.
허용된 제안의 정확도만 보면 40/64에서 28/32로 좋아지지만, 실제로 정확히 완료하는 요청은 줄었다.
따라서 오류 감소 수치 하나로 기본 적용을 정당화하지 않는다.

추가 검증 토큰은 26,744개이며 기존 생성 대비 +33.4%다. 모든 184개 HTTP 생성 응답이 stop으로 종료했고 HTTP 오류는 없었다.
다만 검증 응답 8개는 action/value 모순 또는 근거 불일치로 로컬 검증에 실패했다. HTTP 성공과 유효한 의도 판정은 다르다.
지연은 각 제안 생성 시간과 해당 검증 시간을 더한 값의 중앙값이다. 모의 재생 시간은 제외하며 캐시/부하/실행 순서를 통제한 SLA 실험이 아니다.

### 남은 실패와 잘못된 차단

- `TCI-105`: 실제 생략 요청은 올바른 제안을 만들었지만, 검증 모델이 유효하지 않은 판정을 반환하여 4/4 차단했다.
- `TCI-107`: query에 인용된 low를 실제 설정으로 잘못 읽어, 올바르게 priority를 생략한 제안을 4/4 차단했다.
- `TCI-113`: priority를 지정하지 않은 요청에서도 검증 판정이 실패해 올바른 제안을 4/4 차단했다.
- `TCI-110`: normal을 보내라는 지시와 보내지 말라는 지시가 동시에 유효한데, 생성기와 검증기가 모두 normal을 선택하여 4/4 잘못 허용했다.
- `TCI-111`: 확인이 필요한 미결정 대안 요청은 4/4 차단했지만, 검증기가 정확히 모호함을 인식한 것은 아니다. 한 값을 임의로 선택했고 제안과 충돌해서 막혔다.

명시 값 지정과 부정된 생략 요청은 각각 8/8 올바르게 완료했다. 검증기 출력을 유도하는 한 요청은 4/4 통과했지만,
한 사례로 일반적인 주입 방어를 입증하지 않는다. 두 다른 Tool의 대조 요청은 8/8 그대로 완료했다.
의도 분류는 티켓 56건 중 36건 정답이다. 범위 밖 대조 요청 8건을 포함한 기록상 일치는 44/64다.

수정된 개발/새 실험은 합계 제안 96개, 실제 HTTP 생성 호출 276회, 모의 장애 재생 추적 576개다.
아래의 초기 호환성 실패 실험은 이 성능 집계와 분리한다.

## 구조

```text
원래 요청 + 공개 Tool 목록
  -> 기존 v3 생성: Tool 선택 -> 인자 생성
  -> 변경하지 않은 호출 제안
  -> 공개 스키마 / 문서 ID 검증
  -> create_ticket이면 별도 요청 해석 호출
       입력: 원래 요청 + 공개된 선택 Tool 정보
       제외: 생성된 인자, 평가용 정답, 기대 행동, 장애 시나리오
  -> 검증 응답의 형식 / 원문 근거 / 제안과의 일치 확인
  -> 일치하면 동일 인자 실행, 충돌하거나 검증에 실패하면 차단
```

다른 Tool은 이 우선순위 검증기의 범위 밖이다. 기존 공개 가드는 그대로 적용하지만,
모델이 엉뚱한 Tool을 고르는 오류까지 이 검증기가 차단한다고 주장하지 않는다.
query 내용의 정확성, 실제 외부 서비스 권한, 일반적인 프롬프트 주입 방어도 보장하지 않는다.

### 명시적인 분류 계약

| action | 의미 | 실행 조건 |
| --- | --- | --- |
| `set` | 사용자가 low/normal/high 중 하나를 지정 | 제안의 priority가 같은 값이어야 함 |
| `omit` | priority를 보내지 말라는 지시 | 제안에 priority 키가 없어야 함 |
| `unspecified` | 유효한 priority 지시가 없음 | 제안에 priority 키가 없어야 함 |
| `clarify` | 해소되지 않은 충돌 또는 결정할 수 없는 조건 | 실행 차단, 추가 확인 필요 |

set은 실제 enum 값을, 나머지는 문자열 `none`을 반환한다. `none`은 Tool 인자가 아니라 검증 프로토콜의 표시다.
명시적 결정은 원래 요청의 연속된 부분 문자열을 근거로 제시해야 하며, unspecified의 근거는 빈 문자열이다.
set은 근거에 해당 값이 실제로 포함되어야 한다. 이 검사는 원문 존재 여부만 확인하며 문장의 의미를 증명하지 않는다.

중복 JSON 키, 추가 필드, action/value 모순, 없는 근거, 2,000자 초과 근거, 비정상 종료와 시간 초과는 차단한다.
검증 실패 시 생성 결과를 그대로 실행하는 fallback은 없다. 생성 두 단계와 검증 단계는 같은 120초 예산을 공유한다.
검증 응답과 실패 이유, 입력/출력 사용량, 원시 응답, 변경하지 않은 제안의 해시를 남긴다.

**중요한 제한:** 분류 모델이 부정문을 omit으로 잘못 읽었는데 제안도 priority를 생략했다면 두 오류가 일치하여 통과할 수 있다.
이에 대한 단위 테스트를 포함했다. 원문 인용 검사는 의미 정확성이나 독립적인 안전 보증이 아니다.

## 비교 설계

- 기존 `qwen2.5:1.5b`와 동일한 런타임 식별자, 기존 v3 어댑터를 사용했다.
- 개발 요청 8개와 새 요청 16개를 분리했다. 각 요청은 Tool 정순/역순 및 seed 42/43으로 네 번 관측했다.
- 개발 집합의 `TCI-001/002`는 이전 `TFB-203/304`의 요청을 그대로 가져온 high/low 회귀다.
- 새 집합은 명시 값, 부정된 생략, 실제 생략, 인용된 지시, 부정된 값, 상충 지시, 미결정 대안, 명시적 정정, 값 미지정, 검증기 출력 유도, 다른 Tool을 포함한다.
- 요청 및 기대 행동은 모델 실행 전에 고정했다. 로컬 작성 자료이며 독립적인 사람 검토를 받지 않았다.
- 한 조건에서 v3 제안을 한 번만 생성하고, 검증 OFF/ON의 두 정책에 같은 제안을 전달한다. 서로 다른 재생성 결과를 비교하지 않는다.
- 각 정책은 normal/transient_once/permanent 로컬 장애 환경에서 재생한다. 실제 외부 부작용은 없으며 같은 제안의 재생은 독립 모델 생성이 아니다.
- 이번 실행 fixture는 **실제로 제안된 Tool**에 연결한다. 평가용 정답 Tool을 실행 차단 근거로 사용하지 않는다. 이전 선택 정답 기반 fixture의 성공률과 직접 비교하지 않는다.
- 모호한 요청에는 정답 인자를 만들지 않고 expected_arguments=null로 둔다. 이 경우 기대 행동은 추가 확인이며, 실행 허용 자체가 실패다.
- temperature 0, 호출당 max_tokens 256, 모델 요청 동시성 1이다. 개발 확인 후 새 집합에서 프롬프트나 구현을 다시 튜닝하지 않았다.

### 분리해서 보고하는 지표

| 지표 | 해석 |
| --- | --- |
| 허용 수 | 공개 가드와 해당 정책을 통과한 제안 수 |
| exact 완료 | 실행 가능한 요청에서 Tool/전체 인자가 정답과 같고 실제 허용된 수 |
| 기본값 동등 완료 | 기존 로컬 생략/normal 동등성까지 인정한 완료 수 |
| 잘못된 허용 | 기본값 동등성도 실패한 호출 또는 추가 확인이 필요한 요청을 허용한 수 |
| 정상 제안 차단 | OFF에서 exact인 제안을 ON에서 차단한 수. 분모는 기존 exact 제안 수 |
| 확인 필요 요청 차단 | 모호한 요청을 실행하지 않은 수. 올바른 이유로 모호함을 판별했다는 뜻은 아님 |
| 의도 분류 정답 | 분류 action과 지정 값이 평가용 기대값에 맞는 수. 업무 완료와 별개 |

허용된 호출 중 정확한 비율만 보면 정상 제안을 대량 차단한 손실이 가려진다.
전체 요청 기준 업무 완료 수와 정상 차단 수를 함께 판단한다. 개발/새 집합의 정확도는 합산하지 않는다.

## 호환성 실패 보존

최초 v1 실행은 검증 응답의 `maxLength: 2000` 때문에 로컬 Ollama가 JSON 문법 생성의 반복 확장 한도를 초과했다.
개발 관측 32개 중 티켓 검증 HTTP 요청 28개가 400으로 실패했다. 이때의 차단을 의도 이해 성능으로 해석하지 않는다.

v1.1은 모델 응답용 스키마에서만 이 길이 제한을 제거하고, 로컬 Pydantic 검증에는 2,000자 한도를 그대로 유지한다.
프롬프트와 의미 판정 기준은 바꾸지 않았다. 원래 요청만 사용한 별도 호환성 확인 2회는 공식 실험 분모에 포함하지 않는다.

## 다음 방향

자연어 프롬프트를 계속 덧붙이기보다 **사용자가 확인한 구조화된 요청 제약**을 실행의 기준으로 삼는 방향을 권고한다.
예를 들어 priority는 값 지정/생략을 구분한 입력으로 받고, 애매한 자연어는 확인 전까지 실행하지 않는 방식이다.
이는 모델 정답을 실행 직전에 채워 넣는 보정과 다르며, 사용자 입력 계약과 출처가 별도로 필요하다.
현재 UI/API에는 아직 이 구조화 계약을 연결하지 않았다. 도입 시 프롬프트 재해석 후보와 별도로 평가해야 한다.
