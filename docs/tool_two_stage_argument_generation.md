# Tool 선택과 인자 생성 분리 진단

검증일: 2026-09-09. Evidence Remediation 14.

## 결론

**1.5B 모델에서 인자 보존 개선을 관찰했지만, 기본 어댑터로 승격하지 않는다.**
기존 요청 24회에서 1.5B/v1은 정확한 Tool·인자 조합이 16회에서 24회로 늘었다.
그러나 새 요청에서는 9/12였고, 0.5B는 기존 요청에서 13/24에서 11/24로 후퇴했다.
두 번째 호출은 비용을 늘리고 이미 맞았던 인자를 틀리게 만들 수도 있다.
이 결과는 제한된 로컬 진단이지 일반적인 모델 성능 우위나 운영 준비 완료의 근거가 아니다.

## 구현 구조

```text
공개 요청 + 공개 Tool 목록
  -> 기존 v21 어댑터의 1단계 모델 응답
  -> 선택된 Tool 이름만 유지, 첫 번째 인자는 폐기
  -> 원래 요청 + 선택된 Tool 스키마로 2단계 모델 호출
  -> 엄격한 인자 JSON 파싱
  -> 고정된 Tool 이름과 새 인자로 호출 객체 조립
  -> 기존 비보정 스키마/문서 ID 가드
  -> 진단 실행기의 로컬 모의 도구 및 장애 재현
```

- 1단계는 Tool 이름만 출력하는 새 프롬프트가 아니다. 기존의 전체 Tool 호출 생성 프롬프트를 유지해 비교 변수를 제한했다.
- 2단계에는 정답 Tool, 정답 인자, 첫 번째 인자, 선택하지 않은 Tool 목록, 장애 주입 조건을 넣지 않는다.
- 문서 조회는 런타임의 신뢰된 문서 목록을 전달한다. 공개 요청이 넣은 가짜 문서 목록으로 교체하지 않는다.
- 인자 값을 정답으로 채우거나, 번역·형 변환·필드 제거로 고치지 않는다. 2단계는 새로운 모델 생성이다.
- 2단계가 다른 Tool 이름을 반환해도 Tool을 바꿀 수 없다. 잘못된 JSON, 중복 키, 추가 필드, 형 오류, 미등록 문서 ID는 실행 전에 차단한다.
- 2단계 실패 시 첫 번째 인자로 복귀하지 않는다. 원문과 오류를 남기고 실행을 차단한다.
- 최대 추가 호출은 한 번이다. 2단계는 전체 케이스 시간 예산의 남은 시간만 쓰며 재시도하지 않는다.
- 어댑터 팩토리, API의 허용 어댑터 이름, 기본 프롬프트, 모델 가중치는 변경하지 않았다. 현재는 아래 CLI에서만 사용하는 진단 후보이다.

| 책임 | 파일 |
| --- | --- |
| 공개 입력 필터링, 선택된 스키마, 엄격한 인자 파서 | `backend/app/services/tool_argument_generation.py` |
| 2단계 모델 호출, 실패 차단, 단계별 메타데이터 | `backend/app/services/inference_adapters/two_stage_tool.py` |
| 고정 기준선 검증, HTTP 기록, 비교 실행, JSONL 저널 | `backend/app/reference_workload/tool_two_stage_diagnostic.py` |
| 신규 요청 6개, 정답은 평가기에만 제공 | `reference_workload/diagnostics/tool-two-stage-challenge-v1.json` |
| 독립 재계산, 해시·분모·인자·요청 동일성 검증 | `tools/audit_tool_two_stage.py` |

기존 기준선과 그 기준선이 기록한 8개 구현 파일의 해시는 그대로 유지했다.
어댑터는 호출별 지역 상태만 사용한다. 별도 HTTP 캡처 믹스인은 직렬 진단 전용이며 공유 동시 실행용이 아니다.

## 실험 조건

실제 모델 호출 시간: 2026-09-09 06:05:12~06:10:11 UTC, 한국·일본 시간 15:05:12~15:10:11.
Ollama 0.31.1, Qwen2.5 0.5B/1.5B Q4_K_M. 모델 digest와 런타임 메타데이터를 고정 기준선과 대조했다.

- 기존 요청: 12개 x 런타임/프롬프트 설정 3개 x seed 42·43 = 후보 최종 출력 72개. 이전 기준선 72개는 다시 쓰거나 덮어쓰지 않았다.
- 새 요청: 6개 x 설정 3개 x Tool 정순·역순 x 기본·후보 = 최종 출력 72개. 같은 조건의 두 방식에 seed 42를 사용하고 AB/BA 실행 순서를 교대했다.
- 새 최종 출력은 총 144개, 실제 생성 HTTP 호출은 252회다. 후보 108개는 각각 두 번, 기본 방식 36개는 한 번 호출했다.
- 각 최종 출력을 normal, transient_once, permanent 환경에서 그대로 재사용한 추적은 432개다. 독립 모델 출력 432개가 아니다.
- 모든 HTTP 응답은 `finish_reason=stop`이었고 런타임 오류는 0건이었다. 모든 관측의 사용 토큰을 HTTP 응답에서 확인했다.
- temperature 0, 호출당 max_tokens 256, 케이스 예산 120초, 동시성 1. matrix의 context_length는 선언 메타데이터이며 HTTP 요청에서 강제한 값이 아니다.

## 정확도 비교

지표는 **선택한 Tool과 전체 인자 객체가 명시된 요청값과 정확히 같은 비율**이다.
빠진 선택 인자도 불일치다. 실제 업무 결과의 의미적 정확도나 운영 성공률과는 다르다.

| 설정 | 기존 기준선 | 이번 1단계 | 이번 2단계 최종 | 새 요청 기본 | 새 요청 후보 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.5B / v1 | 13/24 | 13/24 | 11/24 | 6/12 | 9/12 |
| 1.5B / v1 | 16/24 | 16/24 | 24/24 | 7/12 | 9/12 |
| 1.5B / v2 | 14/24 | 15/24 | 20/24 | 6/12 | 9/12 |
| 합계 | 43/72 | 44/72 | 55/72 | 19/36 | 27/36 |

동일 seed라도 재실행한 인자가 항상 같지는 않았다. 따라서 이전 기준선과의 차이와
동일 후보 실행 안에서 1단계에서 2단계로 바뀐 차이를 구분했다.
기존 요청 후보에서는 15건이 개선되고 4건이 후퇴했다. 새 요청 후보에서는 11건이 개선되고 3건이 후퇴했다.
기존 요청의 1단계 HTTP 본문 72개와 새 요청의 기본·후보 쌍 36개의 1단계 본문은 모두 일치했다.
선택 Tool이 달라진 쌍은 두 비교 모두 0건이었다. Tool 목록 순서를 바꾸었을 때 최종 exact 결과가 달라진 경우는 기본 7/18, 후보 3/18이었다.

후보의 조립된 호출 객체는 기존 요청 72/72, 새 요청 36/36에서 스키마를 만족했다.
가드 통과는 각각 70/72, 34/36이었다. 미등록 문서 ID를 생성한 네 건이 차단되었다.
정상 모의 도구 성공은 기존 요청 59/72, 새 요청 31/36으로, 인자 exact 개선과 달리 증가하지 않았다.

### 남은 실패

- Tool 선택 오류는 2단계가 고치지 않는다. 장애 검색을 티켓 생성이나 문서 조회로 잘못 선택하는 문제가 남아 있다.
- 0.5B의 기존 요청 4건은 1단계에서 맞았던 인자가 2단계에서 틀려졌다. 전체 설정에 일괄 적용할 근거가 없다.
- 새 요청 `TFB-104`에서 1.5B/v1·v2는 명시한 `priority="normal"`을 두 순서 모두 생략했다. 엄격한 명시값 보존 지표에서는 실패한다.
- 단, 현재 모의 티켓 핸들러는 priority 생략 시 normal을 적용한다. 이 네 건을 곧바로 실제 업무 의미 오류로 해석하면 안 된다. 이 실험에서는 사후에 점수 기준을 바꾸지 않았다.
- 실제 문서 내용의 정합성, 외부 API의 권한, 운영 장애에서의 모델 자율 복구는 이번 범위가 아니다.

## 비용

아래는 **같은 새 요청 조건을 이번에 함께 실행한 관측**이다. 총 토큰은 입력+출력이며 각 방식 12회 합계다.
시간은 최종 응답까지의 케이스 중앙값이다. 캐시, 실행 순서, 호스트 부하 영향을 통제한 지연 실험은 아니다.

| 설정 | 기본 토큰 | 후보 토큰 | 기본 중앙값 | 후보 중앙값 |

| 0.5B / v1 | 10,771 | 14,264 | 1.111초 | 1.538초 |

단계별 원문·finish_reason·실제 usage·HTTP 본문·요청 해시·지연은 원본 JSON에 있다.

TTFT는 기존 어댑터가 제공하는 1단계 전체 응답 시간의 상한치이며 실제 스트리밍 첫 토큰 시간으로 해석하지 않는다.

## 재현과 증거

저장된 결과만 검증하려면 저장소 루트에서 실행한다. 모델 호출이나 애플리케이션 DB 쓰기는 발생하지 않는다.

```powershell
.venv/Scripts/python.exe tools/audit_tool_two_stage.py
py -3.12 tools/build_tool_two_stage_notebook.py
```

노트북 생성에는 시스템 Python의 nbformat, nbclient, ipykernel이 필요하다. 프로젝트 런타임 의존성에는 추가하지 않았다.
실제 추론을 다시 하려면 Ollama를 실행하고 `backend`에서 **새 출력 경로**를 지정한다.

```powershell
../.venv/Scripts/python.exe -m app.reference_workload.tool_two_stage_diagnostic --repository-root .. --output ../artifacts/reference-workload/tool-two-stage-diagnostic-rerun.json
```

기존 출력이나 저널이 있으면 모델 호출 전에 거부한다. 기준선 파일·소스·입력 또는 모델 런타임 식별자가 바뀌면 비교 실행도 거부한다.
중단 시 이미 쓴 JSONL 저널은 유지된다. 현재 실행기는 중단 지점 이어하기를 지원하지 않으며 새 파일로 재실행해야 한다.
다른 실행을 감사하려면 `--report`로 해당 JSON을 지정한다. 노트북 빌더는 문서화된 v1 결과에 고정되어 있다.

- 원본: `artifacts/reference-workload/tool-two-stage-diagnostic-v1.json`
- SHA-256: `f122e1e6cb38c349b00d8d35769f279a21786a16139f1ab4834eff36558f0ca8`
- 저널: 같은 위치의 `tool-two-stage-diagnostic-v1.observations.jsonl`
- 독립 재계산 및 실행된 노트북: `docs/reports/2026-09-09_tool_two_stage/`
- 검증: 새 테스트 24개 통과, 호스트 전체 391개 통과/1개 건너뜀, Docker 전체 392개 통과. 노트북 전체 실행 완료.

후보의 `raw_output`은 네이티브 모델 Tool 호출이 아니라 **조립된 호출 객체**다.
실제 모델 원문은 `metadata.tool_argument_generation.first_stage/second_stage.raw_output`과 HTTP 응답에 보존된다.
따라서 후보의 `raw_schema_valid`를 기존 네이티브 출력의 형식 준수율과 동일한 지표로 홍보하면 안 된다.

## 운영 상태와 다음 범위

기본값 변경, 공식 평가 결과 등록, 모델 학습, 사용자 검토 승인, Gate 승격을 수행하지 않았다.
Finalized 1.0.4는 기존 64/64 승인, critical 20/20을 유지했다. 공식 상태는
`BLOCKED`, critical failure 110건, 실제 런타임 결과 384건, 실제 출력 검토 0/30,
`not_production_ready`다. 진단 파일의 `human_reviewed=false`, `gate_evidence=false`도 유지된다.

다음에는 1.5B/v1을 후속 실험 대상으로 두되, 이번 실패를 기존 증거에 덮어쓰지 않는다.
선택 인자 보존과 의미적 기본값 동등성의 기준을 먼저 분리하고, 새 미관측 요청에서 검증한다.
그 후 실제 문서 내용·권한 검증과 독립 검토가 확보되어야 API 통합 및 공식 평가 확대를 판단할 수 있다.
